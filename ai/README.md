# Career Quest — Recommendation Engine

Чистый Python 3.9+, без внешних зависимостей, сети и БД. Модуль и исходный
синтетический датасет находятся в `ai/`. Полное веб-приложение подключает этот
модуль; запуск и API описаны в корневом README.md.

## Запуск

Из корня репозитория:

```sh
python3 -m ai E0002
python3 -m unittest ai.test_recommendation -v
```

Для другого набора файлов того же формата:

```sh
python3 -m ai E0002 --data /path/to/dataset --as-of-date 2026-10-01
```

## Интерфейс backend

```python
from ai.data import load_dataset
from ai.recommendation import recommend

employees, events, skills, history = load_dataset("ai/data")
employee = next(e for e in employees["employees"] if e["employee_id"] == "E0002")
result = recommend(employee=employee, events=events, skills=skills, history=history)
```

`employee` — один профиль. `events` — весь JSON-документ или список `events`.
`skills` — весь документ, включая `role_profiles`, а не только каталог навыков.
`history` — список словарей из `csv.DictReader`; функция сама фильтрует сотрудника.
Неизвестные статусы, ссылки, дубли идентификаторов и недопустимые уровни вызывают
ошибку, а не молча превращаются в нулевые значения. Обязательные поля должны
присутствовать. Дополнительные поля допускаются.

Необязательные keyword-аргументы: `as_of_date` (ISO-дата либо `datetime.date`),
`limit` (1–3). По умолчанию используется дата среза из `skills.meta.as_of_date`,
для приложенного kit — **2026-10-01**, независимо от часов компьютера.
Функция не меняет входы; выдача воспроизводима при перестановке событий и истории.

Результат — список из 0–3 объектов с полями:

- `event_id`, `title`, `score` (0–1; относительная оценка, не вероятность);
- `next_session` (дата либо `null` для self-paced), `duration_hours`;
- `factors`: текущая/целевая роль и грейд, источник цели, дата расчёта,
  `skills[]`, сводка истории, компоненты оценки и их взвешенные вклады;
- `reason`: детерминированное объяснение на русском языке.

Каждый элемент `factors.skills` содержит `skill_id`, `name`, `reviewed_level`,
`current_level`, `required_level`, `gap`, `gain`, `max_level`, `effective_gain`,
`gap_closed`, `projected_level`, `critical`. Для UI можно показать
`current_level → projected_level → required_level`. `skill_adjustments` содержит
источник каждого учтённого изменения после оценки навыков.

Пустой список означает отсутствие доступных активностей с положительным вкладом
в целевые требования. До трёх результатов выбираются независимо: это список
вариантов, а не последовательный учебный план с накоплением их будущих эффектов.

## Схема исходных данных

Исходные JSON/CSV из пользовательского архива скопированы без изменения в `data/`.
Подробная документация поставщика: [data/README.ru.md](data/README.ru.md).

| Файл | Фактическая структура |
| --- | --- |
| `employees.json` | `{meta, employees: [...]}`; 200 профилей; `skills` — объект skill_id → уровень |
| `events.json` | `{meta, events: [...]}`; 40 активностей; `develops_skills` — массив `{skill_id, gain, max_level}` |
| `skills.json` | `{meta, proficiency_scale, skills, role_profiles}`; 60 навыков, 32 профиля ролей/грейдов |
| `activity_history.csv` | 2743 строки; `record_id, employee_id, event_id, date, due_date, status, completion_pct, score, feedback_rating, assigned_by` |

Шкала навыков 0–5; отсутствующий навык равен 0. Грейды:
Junior → Middle → Senior → Lead. Требования находятся в
`role_profiles[].required_skills`, критические навыки — в `critical_skills`.
Статусы истории: `completed`, `in_progress`, `dropped`, `no_show`, `declined`,
`overdue`; абстрактных `skipped` и `rejected` в kit нет.

## Правила и явно принятые решения

1. Явная `career_goal` задаёт целевую роль/грейд. Без неё — следующий грейд своей
   роли. Для Lead без цели закрываются оставшиеся требования Lead; новый грейд
   не выдумывается.
2. Завершения строго после `last_review_date` и не позже даты среза применяются
   в хронологическом порядке, с ограничением `max_level` и без уменьшения навыка.
   Завершения до/в дату оценки уже включены в профиль.
3. В CSV нет отдельной даты завершения. Для `completed` используется `date` как
   доступная временная отметка. Для self-paced поставщик описывает её как дату
   зачисления: восстановление уровня в этом случае является приближением.
4. Обязательные HR-активности не рекомендуются и не влияют на предпочтения.
   Ежегодные mandatory-курсы в фактических данных повторяются, хотя общее правило
   README запрещает повторы. Их повторения допустимы. Из добровольных мероприятий
   повторять после завершения можно только `EV_036`.
5. Активности с последним статусом `in_progress` исключены. Отказы, неявки и
   прекращения снижают оценку, но не запрещают участие навсегда.
6. Проверяются текущий грейд, prerequisites и будущая сессия (включая день среза).
   Self-paced доступны без расписания. При смене профессии разрешены события
   текущей или целевой роли; желаемый грейд сам по себе не даёт допуск.
7. Удалённый формат работы не трактуется как запрет очного участия: такого
   ограничения в данных нет. Язык интерфейса не определяет язык мероприятий.
8. Выбираются только события с положительным приростом нужных навыков.
   Полезный вклад ограничен оставшимся разрывом; фактический прирост может быть
   больше него. Равные оценки разрешаются по `event_id`.

## Оценка

Все компоненты нормированы в [0, 1]:

```text
score = 0.35 * grade_importance + 0.30 * skill_gap
      + 0.20 * event_impact + 0.15 * history_fit
```

- `grade_importance`: 1, если активность улучшает критический навык цели; иначе 0.5.
- `skill_gap`: максимальный исходный разрыв среди полезных навыков события / 5.
- `event_impact`: сумма закрываемых разрывов / сумма всех целевых разрывов;
  критические навыки имеют вес 2, остальные — 1 в числителе и знаменателе.
- `history_fit`: `(completed + 1) / (completed + no_show + dropped + 2*declined + 2)`.
  Считаются добровольные участия с пересечением полезных навыков кандидата.
  Каждая запись учитывается один раз, даже при нескольких общих навыках.
  Пустая история даёт нейтральные 0.5. Незавершённые участия не дают прироста.

Веса — объяснимая стартовая эвристика, не обученная модель. Рейтинг учитывает
критичность, размер разрыва, реальный эффект и историю вместо одного минимального
уровня навыка. Длительность выводится пользователю, но не входит в оценку:
личного бюджета времени в kit нет.

## Опциональные LLM-объяснения

```python
from ai.explain import with_llm_explanations

# generate(prompt) — адаптер вашего провайдера, возвращающий строку.
# Адаптер должен сам задавать конечный timeout сетевого запроса.
enriched = with_llm_explanations(result, generate)
```

Модели передаются только выбранные события и структурированные факты, без имени,
ID сотрудника и остальных профилей. Результат помещается в дополнительное
`llm_reason`. Исходный `reason`, оценки и факторы сохраняются: произвольный ответ
LLM не является проверенным источником фактов. Исключения, пустой/нестроковый
ответ или ответ длиннее 2000 символов оставляют детерминированную выдачу.

Конкретный внешний API и ключи не настроены; провайдер не задан. Вся основная
функциональность работает офлайн. Адаптер проверен успешным ответом, ошибкой и
тайм-аутом через тестовые функции; живой вызов LLM не выполнялся.

## Проверка

Тесты включают все 200 исходных профилей, независимые проверки доступности и
эффектов, отсутствие мутаций, воспроизводимость, границы gain/max_level,
критические навыки, историю после оценки, карьерный переход, Lead, повторный
клуб, отрицательную историю и fallback объяснений.

Для исходного kit: 96 сотрудников получают три активности, 35 — две,
37 — одну, 32 — ни одной. Каталог конечен; неподходящие или уже завершённые
активности не добавляются для заполнения TOP-3.

## Интеграция с сохранённым прогрессом

Веб-приложение хранит выполненные шаги в SQLite. `skill_snapshot_date` —
дата материализованного снимка навыков после выполнения, `reviewed_skills` —
исходные уровни оценки. Эти дополнительные поля создаются приложением;
исходный kit их не требует. История после границы снимка применяется один раз.
`last_review_date` сохраняет дату оценки, а не дату клика.
Клуб EV_036 не предлагается повторно в день уже зачтённого участия.

Опциональный локальный Ollama-адаптер: `ai/local_llm.py`; переменная
`CAREER_QUEST_OLLAMA_MODEL`. Он не заменяет факторы или исходное объяснение.
